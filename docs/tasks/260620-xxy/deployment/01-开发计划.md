# 开发计划：4 个待写脚本各是干啥的，怎么串起来

> 用途：在我真正写代码之前，先让你看懂"将要有哪些脚本、每个干啥、它们怎么连成一条链"。
> 不陷代码细节，用大白话 + 比喻讲清楚。
> 配套：`00-心智模型.md`（全局认知）、`02-Mac-mini-部署文档.md`（照着敲）。

## 先看全局：一条流水线

每天早上要做的事，本质是一条**流水线**，4 个待写脚本是流水线上的 4 个工位，加上 2 个已经写好的工位，一共 6 步：

```
                              ┌──────────── run_daily.sh（总指挥）────────────┐
                              │                                                │
   ① 拉数据         ② 推理            ③ 出报告           ④ 推送              │
fetch_daily_data.py → predict.py → report.py → notify.py                      │
  (已有)            (已有)         (待写)       (待写)                         │
                              └────────────────────────────────────────────────┘
                                          ↑
                              run_daily.sh 负责把①②③④按顺序串起来、管错误、记日志（待写）

   ⑤ launchd .plist：闹钟，每天 08:00 把 run_daily.sh 叫起来（待写）
```

一句话：**`run_daily.sh` 是总指挥，按顺序调用 4 个干活的脚本；`.plist` 是闹钟，负责每天准时叫醒总指挥。**

## 逐个讲：每个脚本干啥

### 已有脚本（回顾，不用再写）

**`scripts/fetch_daily_data.py`（已有）— 数据搬运工**
- 干啥：联网从 Yahoo Finance 拉 SPY/VIX/breadth 最新行情，存成本地 CSV。
- 比喻：每天早上去菜市场买最新鲜的菜。
- 为什么需要：模型要算"今天"的概率，得先有"今天"的数据。

**`ml/predict.py`（已有）— 算命先生**
- 干啥：加载模型文件，读最新数据，算出"今天 SPY 处于底部区域的概率"，连同 feature importance、数据新鲜度一起输出成一个 JSON 文件。
- 比喻：拿着菜（数据）和食谱（模型），算出一道菜的评分。
- 输出：`output/daily_prediction.json`（一个结构化的结果文件，给下一步用）。

### 待写脚本（这轮要规划的）

### 待写 ① `ml/report.py` — 文案编辑

- **干啥**：读 `predict.py` 吐出的 JSON，把里面冷冰冰的数字，整理成一份**人能读的 Markdown 报告**。
- **比喻**：算命先生给了一堆数字，文案编辑把它写成一篇"今日运势"。
- **输入**：`output/daily_prediction.json`
- **输出**：`reports/2026-06-20.md`（按日期命名的报告文件）
- **报告里会有什么**：
  - 日期、SPY 收盘价
  - 今天是不是信号日（醒目标注）
  - 底部区域概率（百分比）
  - feature importance Top 几名 + 每个特征当前的值（让你知道"模型为什么这么判断"）
  - 数据新鲜度（三个数据源各更新到哪天，防止用了过期数据）
  - 风险提示（"仅供研究"，非信号日额外提示）
- **使用场景**：每天自动跑；你也可以平时手动跑一次看看格式。

### 待写 ② `ml/notify.py` — 信使

- **干啥**：把报告的关键内容，通过 Telegram 推送到你手机。
- **比喻**：把写好的"今日运势"用快递寄到你手上。
- **输入**：报告内容（或直接读 JSON 的关键字段）
- **输出**：你手机上的一条 Telegram 消息
- **需要的配置**：Telegram 的 `bot token` 和 `chat id`（存在 `.env` 里，不进 git）
- **为什么单独一个脚本**：推送逻辑独立出来，将来想换渠道（邮件/Bark）只改这一个文件，不动其他。

### 待写 ③ `scripts/run_daily.sh` — 总指挥 / 工头

- **干啥**：按顺序把上面的脚本一个个调起来，并且**管好出错和日志**。这是最关键的"粘合剂"。
- **比喻**：工头，拿着清单挨个喊工人干活，哪个工人没干成就记下来、打电话报告。
- **内部逻辑（按顺序）**：
  1. 激活 Python 虚拟环境（venv）
  2. 等几秒 + 探测网络是否通（防止 Mac 刚睡醒网还没连上）
  3. 调 `fetch_daily_data.py` 拉数据 —— 失败就重试，还失败就推送告警并停
  4. 调 `predict.py` 推理
  5. 调 `report.py` 出报告
  6. 调 `notify.py` 推送
  7. 全程把输出写进 `logs/daily_YYYYMMDD.log`
- **为什么需要它**：launchd 只会"叫醒一个脚本"，不会自己按顺序跑 4 个。必须有一个总指挥把它们串起来。而且**错误处理**（重试、告警、日志）都集中在这里——这样某天跑挂了，你能从日志和告警知道哪一步出的问题。
- **使用场景**：launchd 每天自动调它；部署时你也手动跑它一次做验证。

### 待写 ④ `deploy/com.quant.daily.plist` — 闹钟

- **干啥**：一个 macOS 的配置文件（XML 格式），告诉系统"每天 08:00 帮我跑一下 run_daily.sh"。
- **比喻**：定好的闹钟。
- **里面写什么**：
  - 跑哪个脚本（`run_daily.sh` 的绝对路径）
  - 几点跑（`StartCalendarInterval`: 8 点 0 分）
  - 日志写哪（标准输出/错误重定向到日志文件）
- **使用场景**：放到 Mac mini 的 `~/Library/LaunchAgents/` 目录，用 `launchctl` 装载一次，之后就天天自动了。
- **注意**：它本身不"运行"，它只是个配置；真正的定时能力是 macOS 的 launchd 系统读了这个配置后提供的。

## 它们怎么串成一条链（数据怎么流动）

```
launchd 闹钟（08:00）
   │ 叫醒
   ▼
run_daily.sh（总指挥）
   │ 第1步：激活环境 + 检查网络
   │ 第2步：调用 ↓
   ▼
fetch_daily_data.py ──写──▶ data/*.csv（最新行情）
   │
   ▼ run_daily.sh 第3步：调用
predict.py ──读 data/*.csv + models/模型 ──写──▶ output/daily_prediction.json
   │
   ▼ run_daily.sh 第4步：调用
report.py ──读 daily_prediction.json ──写──▶ reports/2026-06-20.md
   │
   ▼ run_daily.sh 第5步：调用
notify.py ──读报告/JSON ──▶ Telegram ──▶ 你的手机
   │
   ▼
全程日志 ──写──▶ logs/daily_20260620.log
```

**关键理解**：脚本之间不是直接"对话"，而是通过**文件**接力——前一个把结果写成文件，后一个读这个文件。这样每一步都可以单独跑、单独排查（比如报告不对，单独跑 report.py 看就行）。

## 配置文件（不进 git 的敏感信息）

**`.env`** —— 存放密钥，**绝不进 git**（`.gitignore` 已忽略）：
```
TELEGRAM_BOT_TOKEN=你的bot令牌
TELEGRAM_CHAT_ID=你的聊天ID
# YAHOO_PROXY=如需代理才填（你的 Mac mini 网络干净，预计不用）
```

## 开发顺序（我下一轮会按这个写）

1. `report.py`（先能出报告，本地就能看效果）
2. `notify.py`（先能推送，单独测一条消息通不通）
3. `run_daily.sh`（把 1、2 和已有脚本串起来 + 错误处理 + 日志）
4. `.plist`（最后做闹钟）

每写完一个都能单独验证，不用等全部写完才知道对不对。
